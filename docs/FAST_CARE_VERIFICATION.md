최종 핵심 회귀는 8개 중 위 6개가 먼저 통과했고, 새 타이머 표시 검사는 표시 갱신 주기를 반영한 뒤 실패 항목 2개만 재실행해 통과했습니다. HUD는 약 0.1초마다 표시하므로 ×8에서는 읽은 표시가 최대 약 0.8초 뒤처질 수 있습니다. 내부 경과 1초당 정확히 8초 감소하는지, 콤보는 실제 3초인지와 상태 전환 시 정산은 별도 단위 검사로 검증합니다. 실패를 숨기거나 같은 검사 전체를 무작정 반복하지 않았습니다.

관련 기능을 먼저 검사하고, 통합 단위 검사는 한 번 실행했습니다. 타입 오류를 수정한 뒤 빌드만 다시 실행했고, 마지막 보상 호환성 보강 뒤에는 해당 보상/새 규칙 검사와 빌드·Deno·정산 경로만 재확인했습니다. 영단어·가구 전체 브라우저 검사나 장시간 5분 실측을 반복하지 않았습니다. GitHub의 기존 전체 CI 설정 자체는 유지합니다.

## 필수 안전 검증

- 새 도전의 기본 점수 2배, 스테이지 점수 보존, /500 기본 코인과 기존 콤보/유지 보너스.
- 연쇄 종료 뒤 점수에 해당하는 최종 단계로 직행, 보드 임의 교체 없음, 7단계 배율, 별도의 3초 콤보, 최소 두 유효 교환.
- 시각/비시각 엔진이 같은 점수·보드·최소 연출 단계 수를 생성하고 서버는 화면 배열을 만들지 않음.
- **변경 전 코드로 생성한 v4 고정 기록** 두 개를 보관했습니다. 새 서버에서도 최종 보드/점수와 4,022·4,130코인이 정확히 일치합니다.
- 기존 v4 미지급 세션을 새 서버에서 정산하고 같은 영수증 재시도는 재지급하지 않음. v5 세션을 v4로 위장해 높은 /250 공식으로 청구하면 거절.
- 압축된 좌표/시간 튜플을 원래 기록으로 정확히 복원, 작은 검증 조각/한 번의 검증 결과 일치, 변조 입력 거절.
- PostgreSQL 호환 PGlite에서 실제 SQL로 권한·동시/중복 지급·실패 롤백·원래 사진/잔액 외 필드 보존·오래된 월드 갱신 충돌을 확인.
- 일괄 쓰다듬기 개별 6시간 제한과 행복/친밀 효과, held/탐험/수면 제외, 일괄 목욕 하루 4회/30분/날짜 변경/완료 회복.
- 음식 수량 부족/0개/고정 순서/한 명당 하나/각자 10초와 공통 1.5초 간격/좋아함 1.5·싫어함 0.8/상태 100 상한.
- 기존 월드 operation UUID/SQL 영수증으로 food·pet·bath 명령 재전송이 음식이나 보상을 재차 변경하지 않음.
- PC·모바일 UI 연속 클릭과 수량 자동 갱신, 한 행동에 서버 명령 하나, 다른 기기에서 감소한 인벤토리와 목욕 횟수 확인.

사천성/영단어 소스, 기존 `src/cloud/client.ts`와 `src/cloud/server.ts`는 기준 main과 동일합니다. 공유 명령 엔진에는 세 일괄 명령 분기만 추가했고 기존 사천성 분기를 변경하지 않았습니다. 실제 iPhone Safari 검증과 운영 Edge 네트워크 지연 측정은 하지 않았습니다.

## 지연 원인과 재현

```bash
node scripts/fast-update-measure.mjs
MATCH3_SAMPLES=10 node scripts/fast-challenge-balance.mjs
```

기존 교환/콤보 계산은 이미 로컬이었으며 게임 중 새 보상 통신이 없었습니다. 불필요한 매치별 서버 검증을 새로 추가하거나 기존 검증을 없애지 않았습니다. 개선 대상은 종료 후 반복 요청과 화면 배열/전송량, 캐릭터별 반복 요청입니다.

- 수정 전 고정 v4 100수 기록은 80수 제한 때문에 2개 정산 요청이 필요했습니다. 로컬 단일 계산 측정은 시드별 약 143/111ms였습니다(콜드 단일 표본).
- 수정 후 각 시드 10회, 모두 한 요청 분량으로 완료했습니다. 반복 계산 중앙값은 약 139/119ms입니다. 256수·250ms 예산으로 제한하며 장기 판은 여전히 나누어 검증합니다. 원래 계산 자체가 수백 ms 미만이어서 큰 CPU 가속을 입증했다고 주장하지 않습니다.
- 별도 동일 100수 엔진 비교는 시각 출력 약 116.6ms·비시각 약 99.2ms였고 화면 보드 스냅샷 슬롯 43,392개가 0개가 되었습니다. 이 시간 비교는 단일 쌍 측정입니다.
- 같은 새 기록 본문은 4,262→1,821바이트로 약 57% 감소했습니다. 외부 HTTP 헤더/세션 ID는 제외한 기록 본문 크기입니다.
- 일괄 행동은 친구 수만큼 요청하지 않고 한 명령/한 원자적 commit으로 처리합니다. 응답에 포함된 최신 상태를 이용하고 추가 전체 조회를 보내지 않습니다.
- 지급된 영수증은 재검증하지 않고 진행 체크포인트는 이어 계산합니다. 권한·시드·입력/시간·버전·원자성 검증은 유지했습니다.

원격 네트워크/Edge 지연은 운영 접근 없이 측정하지 못했습니다. 위 결과는 로컬 엔진과 테스트 네트워크 기준이며 실제 서비스 대기시간이 특정 배수로 줄었다고 보장하지 않습니다. [원시 측정 JSON](FAST_CARE_MEASUREMENTS.json)

## 플레이 시간 목표

요청한 점수/배율을 그대로 적용한 반응 시간 모델 5종 × 10시드, 총 50판입니다. 실제 사람의 실력/반응을 측정한 실험은 아닙니다.

| 가정 | 조작 가능 생존 중앙값 | 연출 포함 중앙값 |
| --- | ---: | ---: |
| 초보 | 33.3초 | 38.8초 |
| 일반 | 39.1초 | 46.4초 |
| 숙련 | 43.1초 | 54.8초 |
| 빠른 | 42.0초 | 55.5초 |
| 항상 1초 만에 정답 선택 | 31.9초 | 55.0초 |

모델에서는 목표 1~4분보다 짧게 끝났습니다. 점수 상승 속도에 따라 상위 배율에 진입하는 시점도 달라 결과가 실력순으로 단조롭지는 않습니다. 특히 Lv.7에서는 +5초가 실제 0.625초 분량이라 1초 정답 봇도 계속 생존할 수 없습니다. **목표 플레이 시간을 충족했다고 표시하지 않습니다.** 요청한 표의 숫자를 우선 유지했고, 실사용자 플레이로 추가 조정이 필요할 수 있습니다.
