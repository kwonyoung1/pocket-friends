# 빠른 도전·캐릭터 일괄 관리 업데이트

기준 main: `8e50af1`. 사천성·영단어 소스 및 기존 CloudClient/게임 HTTP 처리·동기화 방식은 유지합니다. 캐릭터·사진·코인·탐험·장비·가구·스테이지 진행을 초기화하지 않습니다.

## 도전 모드 변경

**새 도전(v5)에만** 제거 기본 점수와 특수 생성 보너스를 2배 적용합니다. 보석 50→100점, 4개 생성 100→200점, 5개/폭발 생성 200→400점입니다. 콤보·낙하 연쇄 배율 및 최종 ×8 상한은 그대로입니다. 배율 적용 후 정수 반올림하므로 일부 반점 연쇄는 이전 최종 점수의 단순 두 배와 1점 차이가 날 수 있습니다. 30개 스테이지의 점수/목표는 바꾸지 않습니다.

| Lv. | 진입 점수 | 실제 1초당 타이머 소모 |
| --- | ---: | ---: |
| 1 | 0 | 1.5초 |
| 2 | 3,000 | 2.0초 |
| 3 | 8,000 | 2.7초 |
| 4 | 15,000 | 3.5초 |
| 5 | 25,000 | 4.5초 |
| 6 | 40,000 | 6.0초 |
| 7 | 60,000 | 8.0초 |

큰 점수로 여러 구간을 넘으면 해당 연쇄가 완전히 끝난 뒤 최종 단계로 바로 올라갑니다. 기존 경과 구간을 먼저 정산하고 다음 조작 가능 시간부터 새 배율을 적용합니다. 현재 보드는 난이도 때문에 초기화하지 않습니다. 최소 두 유효 교환과 자동 섞기를 유지합니다.

시작 30초·직접 교환마다 +5초·최대 30초·3초 콤보를 유지합니다. 폭발/낙하/섞기/계산/일시정지는 시간에서 제외합니다. Lv.7에서 시간을 계속 유지하려면 평균 0.625초보다 빨리 매치를 성공해야 합니다. 콤보 3초에는 난이도 배율을 곱하지 않습니다. LEVEL 배너·배율·테두리·기존 선택적 경고음을 표시하며 보드를 가리지 않습니다.

보상 기본값은 **floor(점수/500)**으로 바꾸고 최고 콤보/유지 보너스는 그대로입니다. 같은 제거 실적이 점수 2배만으로 코인 2배가 되지 않게 합니다. 예: v4 200,000점·32콤보·65초와 v5 400,000점·32콤보·65초는 모두 3,650코인입니다.

진행 중이던 v4 세션과 미지급 기록은 v4의 점수·시간·/250 공식으로 검증합니다. 기존 세션 행을 새 규칙으로 바꾸지 않습니다. 새 v5 세션은 서버가 발급하고 v4로 위장해 /250 보상을 받을 수 없습니다. 예전 브라우저의 새 시작은 새로고침을 안내하지만 이전 세션 정산은 계속 허용합니다. 최고 기록·설정 키는 유지합니다.

## 일괄 관리 사용법

- **생활·입양 → 친구 생활 → 모두 놀아주기**: 기존 일반 쓰다듬기와 동일한 행복 +2·친밀 +1 및 기존 XP 조건입니다. 캐릭터별 6시간 보상 쿨타임을 그대로 씁니다.
- **같은 위치 → 모두 씻기**: 기존 30분 목욕을 시작합니다. 즉시 청결을 채우는 새 규칙이 아닙니다. 캐릭터별 하루 4회·한국 날짜 초기화·진행 중 목욕 제한과 완료 효과를 유지합니다.
- **인벤토리 → 음식 → 원하는 음식 카드의 일괄 주기**: 보유 수량/보유 친구/실행 가능 인원/필요 수량/지급 예정 수량과 이름을 확인한 뒤 **확인하고 일괄 주기**를 누릅니다. 목록 순서대로 한 명당 한 개입니다. 부족하면 그 수량만 처리합니다.

탐험·수면·목욕·교감 중이거나 제한에 걸린 친구는 건너뜁니다. 음식의 캐릭터별 10초 제한과 기존 사용 후 1.5초 간격은 유지합니다. 일괄 명령의 시작 때 공통 사용 간격을 한 번 검사하고, 한 트랜잭션 안에서는 여러 친구에게 한 개씩 지급한 뒤 다음 사용 간격을 유지합니다. 다른 개별 명령에는 이 내부 묶음 처리를 허용하지 않습니다. 좋아함 ×1.5·싫어함 ×0.8·기본 사료 예외·상태 상한은 기존 `useItem`을 재사용합니다.

성공·쿨타임·일일 제한·외출/수면/교감·음식 부족·실패 인원을 결과로 표시합니다. 확인 뒤 다른 기기의 상태가 바뀌었을 수 있어 서버에서 다시 판정합니다. 동시에 보이는 짧은 하트·비누/식사 말풍선은 최대 6명입니다. 사진 얼굴과 기존 캐릭터를 변경하지 않습니다.

서버는 `care-play-all / care-wash-all / care-feed-all` 중 **한 명령만** 받습니다. 기존 operation UUID·영수증·revision/CAS·월드 원자적 commit을 재사용합니다. 재전송은 같은 영수증을 읽어 음식이나 보상을 중복 처리하지 않습니다. 연속 클릭은 UI 잠금과 서버의 개별 제한 양쪽에서 방지합니다. 새로운 일괄 관리 DB 테이블은 필요하지 않습니다.

## 대기시간 개선과 측정

기존 교환/매치는 원래부터 로컬 처리였고 게임 중 별도 보상 API를 보내지 않았습니다. 이 경로를 유지했습니다. 기존 월드의 5초 확인/실시간 연결도 그대로이며, 일괄 실행 후 추가 전체 조회를 보내지 않고 명령 응답으로 갱신합니다.

측정 가능한 병목은 종료 후 **80수마다 반복하던 보상 검증 요청**, 검증 중 만들어지던 화면용 보드 배열, 반복 키가 많은 JSON 기록이었습니다.

| 항목 | 전 | 후 |
| --- | --- | --- |
| 100수 정산 표본 | 2회 요청 필요 | 두 고정 시드 각 10회 측정 모두 1회 |
| 한 번에 검증할 수 있는 상한 | 80수 | 최대 256수·약 250ms 작업 예산 뒤 체크포인트 |
| 별도 100수 엔진 경로의 보드 스냅샷 슬롯 | 43,392개 | 0개 |
| 같은 v5 입력 기록 JSON | 4,262바이트 | 1,821바이트(약 57% 감소) |

서버는 화면 스냅샷·이동/광선 출력 배열을 만들지 않고 점수·보드 논리·시간 하한에 필요한 단계 정보만 계산합니다. 같은 엔진의 시각/비시각 결과와 v4 정산 금액이 일치하는지 검사했습니다. 긴 판은 CPU 예산에 따라 계속 나누어 검증하며 성공한 체크포인트를 재활용합니다. 지급 영수증이 있는 세션은 재계산하지 않습니다. 압축 기록은 한 번 준비해 요청마다 재사용합니다.

원격 Supabase 지연은 운영 프로젝트에서 측정하지 않았습니다. 로컬 반복 재생의 중앙값은 두 시드에서 약 139ms/119ms였고, 화면 스냅샷 생략 경로의 별도 단일 비교는 약 117→99ms였습니다. 조건이 다른 이전 단일 측정과 비교해 큰 CPU 가속 배수를 주장하지 않습니다. 주요 확정 개선은 요청 수·스냅샷 할당·전송량 감소입니다. 권한·시드·순서·시간·버전·중복 지급·원자적 정산 검증은 유지합니다.

## 밸런스 목표의 한계

요청한 수치를 그대로 적용했습니다. 50판 반응 시간 모델의 일반/숙련 가정은 연출 포함 중앙값 약 46/55초로 목표 1~3분보다 짧았습니다. 실제 사람의 측정은 아니며 목표 플레이 시간을 달성했다고 주장하지 않습니다. 표의 수치를 우선 보존했으며 실플레이로 조정이 필요할 수 있습니다. [측정/검증 상세](FAST_CARE_VERIFICATION.md)
