# A단계: 클라우드 연결 설정과 배포

이번 브랜치는 **A단계의 코드**입니다. B~D단계의 생활·가구·햄스터·신규 캐릭터 콘텐츠는 아직 구현하지 않았습니다. 기존 네 친구, 교감, 성장, 상점, 탐험, 사진, 로컬 저장은 유지합니다.

실제 Supabase 프로젝트가 아직 연결되지 않았습니다. 로컬 자동 검증과 실제 서비스 검증을 구분해 주세요. 아래 설정을 완료하기 전에는 PC·모바일 동기화나 비밀번호 보호가 운영 사이트에 적용되지 않습니다.

## 1. 현재 코드 확인 결과

- 최신 main `d10d6cc`에서 새 브랜치 `feat/cloud-foundation`을 만들었습니다. 기존 PR #3의 게임과 이동 검사 수정이 병합되어 있습니다.
- 기존 저장소는 localStorage `pocket-friends-v1`, IndexedDB `pocket-friends-stage-two` / `saves`입니다.
- 초기 상태의 단위 테스트 36개, PC·모바일 브라우저 테스트 40개, 배포 빌드가 통과했습니다.
- 게임의 좌표계는 1000×640이며 가구를 피하는 경로 탐색과 Pointer Events 기반 교감/드래그를 사용합니다. 방 밖의 목록은 계속 스크롤할 수 있습니다.

## 2. 무엇을 직접 설정해야 하나요?

코드는 준비되어 있지만 Supabase 계정 생성, 프로젝트 생성, 비밀번호·토큰 입력은 본인 계정에서 해야 합니다. 이 작업에서 외부 프로젝트를 만들거나 유료 플랜을 신청하지 않았습니다.

Supabase 무료 플랜으로 시작할 수 있으나 저장 공간·전송량·실행 횟수 제한과 장기 비활성 프로젝트 중지 정책은 가입 화면에서 확인하세요. 사진도 데이터베이스 스냅샷에 포함되므로 사용량에 영향을 줍니다. 유료 플랜을 선택할 필요는 없습니다.

**먼저 기존 게임의 맨 아래 `추억 보관`을 눌러 PC와 모바일 각각의 백업 파일을 받으세요.**

### 2-1. Supabase 프로젝트 만들기

1. [Supabase Dashboard](https://supabase.com/dashboard)를 열고 **Sign in**으로 로그인합니다.
2. **New project**를 클릭합니다. 조직이 없으면 안내에 따라 개인 조직을 만듭니다.
3. 프로젝트 이름을 `pocket-friends`로 정합니다. 데이터베이스 비밀번호는 별도의 긴 비밀번호로 만들고 개인 비밀번호 관리 도구에 보관하세요. 게임 접속 비밀번호와는 다른 값입니다.
4. 사용할 지역을 선택하고 **Create new project**를 누릅니다. 준비 완료까지 기다립니다.
5. 프로젝트 **Settings → General**에서 **Project ID / Reference ID**를 확인합니다. 메뉴 이름은 Supabase 화면 개편에 따라 조금 다를 수 있습니다.
6. **Connect** 또는 **Settings → API / API Keys**에서 **Project URL**과 **Publishable key**를 확인합니다. 구형 키 메뉴라면 `anon` 키를 사용해도 됩니다.

`secret` 키와 `service_role` 키는 프런트엔드나 GitHub 변수에 넣지 마세요. 빌드 검사도 이러한 키를 거부합니다. 서버에 필요한 서비스 역할 키는 Supabase가 Edge Function에 자동 제공하므로 직접 복사할 필요가 없습니다.

### 2-2. 기기 인증 켜기

1. 왼쪽 **Authentication → Sign In / Providers**를 엽니다.
2. **Anonymous Sign-Ins** 또는 **Anonymous** 항목을 켜고 **Save**를 누릅니다.
3. 일반 방문자는 이 단계만으로 게임 데이터에 접근할 수 없습니다. 서버에서 공통 비밀번호를 확인한 기기에만 만료 시간이 있는 월드 멤버십을 추가합니다.

각 기기는 서로 다른 Supabase 인증 세션을 사용하지만 모두 하나의 `home` 월드에 연결됩니다. 개인정보나 이메일 가입은 필요하지 않습니다.

### 2-3. 데이터베이스와 접근 권한 설치하기

1. GitHub에서 [마이그레이션 SQL](../supabase/migrations/202610150001_cloud_world.sql)을 엽니다.
2. 파일 오른쪽 위 **Copy raw file** 아이콘을 눌러 전체 내용을 복사합니다.
3. Supabase 왼쪽 **SQL Editor → New query**를 클릭합니다.
4. 빈 편집기에 붙여넣고 **Run**을 누릅니다. 이 SQL은 새 테이블·정책·함수를 설치하며 기존 브라우저 게임을 삭제하지 않습니다.
5. 성공 메시지를 확인합니다. **Table Editor**에서 `game_worlds`에 `home` 행이 하나 있고 `data`는 비어 있는지 확인합니다.

이 설치 SQL은 새 프로젝트에서 **한 번만** 실행합니다. 테이블이 이미 있다는 오류가 나면 반복 실행하거나 테이블을 지우지 말고 오류 내용을 확인하세요. Realtime 공개 테이블에는 `game_worlds`만 추가합니다. 비밀번호와 로그인 제한 기록을 Realtime에 공개하지 않습니다.

### 2-4. 서버 비밀번호와 사이트 주소 설정하기

1. Supabase 왼쪽 **Edge Functions → Secrets**를 엽니다.
2. **Add new secret**를 누르고 이름에 `GAME_ACCESS_PASSWORD`, 값에는 **요청하신 초기 접속 비밀번호**를 직접 입력한 뒤 저장합니다. 비밀번호 값은 이 문서와 저장소에 적지 않았습니다.
3. 같은 방법으로 `GAME_ALLOWED_ORIGINS`를 추가합니다. 현재 GitHub Pages의 값은 `https://kwonyoung1.github.io`입니다. 끝에 `/pocket-friends/`를 붙이지 않습니다. Origin은 도메인까지만 사용합니다.
4. 비밀번호 변경도 이 Secrets 화면에서 합니다. 새 비밀번호는 이후 입장 시도에 적용됩니다. 기존 기기 세션까지 즉시 차단하려면 아래 세션 해제 절차도 수행하세요.

공통 비밀번호는 가족·소규모 공유 월드 용도입니다. 짧은 숫자 비밀번호는 추측에 취약하므로 장기 사용에는 긴 무작위 비밀번호를 권장합니다. 서버는 모든 기기의 비밀번호 제출을 합쳐 **15분당 최대 10회**로 제한합니다. 의도적인 반복 시도로 정상 입장도 잠시 막힐 수 있습니다. 공개 서비스 수준의 개인별 접근 제어가 필요하면 Supabase 이메일/패스키 계정과 관리자가 승인하는 멤버십으로 확장하는 것이 안전한 대안입니다. 현재 버전에 이메일/패스키 로그인은 구현하지 않았습니다.

### 2-5. GitHub에서 서버 배포용 설정하기

서버 배포는 수동 실행 워크플로를 준비했습니다. 로컬 컴퓨터에 개발 도구를 설치할 필요는 없습니다.

1. Supabase 프로필 메뉴에서 **Account preferences / Account settings → Access Tokens**를 엽니다. 프로젝트의 API 키 화면과는 다릅니다.
2. **Generate new token**을 누르고 서버 배포용 토큰을 만듭니다. 토큰은 채팅이나 공개 파일에 붙여넣지 마세요.
3. GitHub 저장소 **Settings → Secrets and variables → Actions → Secrets → New repository secret**를 누릅니다.
4. Name에 `SUPABASE_ACCESS_TOKEN`, Secret에 방금 만든 토큰을 넣고 **Add secret**를 누릅니다.
5. 같은 화면의 **Variables → New repository variable**에서 아래 공개 변수들을 만듭니다.

| 변수 이름 | 넣을 값 |
|---|---|
| `SUPABASE_PROJECT_REF` | Supabase Project ID / Reference ID |
| `VITE_SUPABASE_URL` | `https://프로젝트ID.supabase.co` 형태의 Project URL |
| `VITE_SUPABASE_ANON_KEY` | Publishable key 또는 구형 anon 키 |
| `VITE_CLOUD_ENABLED` | 우선 `false`; 서버 검증 후 `true`로 변경 |

게임 비밀번호는 Supabase Secrets에만 두며 `VITE_` 변수에는 넣지 않습니다. 공개 URL과 공개 키만 웹사이트 빌드에 포함됩니다.

## 3. PR 병합과 첫 배포

1. [새 PR 만들기](https://github.com/kwonyoung1/pocket-friends/compare/main...feat/cloud-foundation?expand=1)를 열고 **Create pull request**를 누릅니다. PR의 자동 검사 결과가 초록색인지 확인합니다.
2. **Merge pull request → Confirm merge**를 누릅니다. 클라우드 플래그가 `false`이므로 기존 로컬 게임이 유지됩니다. 이 상태는 비밀번호로 보호되는 사이트가 아닙니다.
3. **Actions → Deploy cloud backend (manual) → Run workflow**를 누릅니다. Branch는 **main**을 고르고 초록색 **Run workflow** 버튼을 누릅니다.
4. 서버 배포가 초록색으로 완료되는지 확인합니다. Supabase **Edge Functions**에 `game`이 나타나야 합니다.
5. `VITE_CLOUD_ENABLED` 변수를 `true`로 바꿉니다.
6. **Actions → Test and deploy Pocket Friends → Run workflow → main → Run workflow**를 실행합니다.
7. 빌드·검사·Pages 배포가 모두 초록색이 되면 **Settings → Pages → Visit site**를 누릅니다. 기존 사이트 주소를 유지합니다.
8. 게임 화면보다 먼저 비밀번호 화면이 나타나는지 확인하고, 정한 비밀번호로 입장합니다.

URL/공개 키가 빠졌거나 비밀 키를 잘못 넣으면 클라우드 빌드를 실패시킵니다. 인증 오류 때 기존 로컬 게임을 자동으로 열어 주는 우회 경로는 없습니다.

## 4. PC와 모바일 데이터 중 어떤 것을 사용할까요?

**더 오래 키운 데이터를 가진 기기부터 접속하세요.** 두 기기를 동시에 초기 설정하지 마세요.

1. 비밀번호로 입장하면 이 기기 데이터와 클라우드 데이터를 비교하는 화면이 나타납니다.
2. 아직 클라우드가 비어 있으면 **기존 데이터 파일 백업**을 먼저 누릅니다.
3. 다른 기기에서 받은 JSON을 사용하려면 **백업 파일에서 원본 선택**에서 해당 파일을 고릅니다. 기기 원본은 덮어쓰지 않고 미리보기만 바뀝니다.
4. **이 기기 데이터를 기준으로 가져오기 → 확인하고 공유 월드 만들기**를 누릅니다. 기존 사진·이름·상태·코인·인벤토리·성장·진행 중 탐험을 한 번 복사합니다. 새 시작 코인을 더하지 않습니다.
5. 기존 게임을 쓰지 않으려면 **새 공유 월드로 시작하기**를 선택할 수 있습니다. 이 경우에도 기존 기기 원본은 삭제하지 않습니다.
6. **이 클라우드 월드 사용하기**를 누릅니다.
7. 다른 기기에서도 같은 URL과 비밀번호로 입장합니다. 저장된 로컬 데이터와 클라우드 데이터가 다르게 표시되어도 합산하지 않습니다. **이 클라우드 월드 사용하기**로 이미 만든 월드에 참여합니다.

초기 원본 선택은 한 번만 가능합니다. 동시 요청은 데이터베이스에서 하나만 승인합니다. 이미 만든 클라우드 월드를 다른 기기의 백업으로 덮어쓰는 일반 사용자 기능은 제공하지 않습니다. 잘못된 원본을 선택했다면 양쪽 기기와 클라우드 백업을 보관한 뒤 관리자 복구를 진행해야 합니다. 데이터베이스 행을 임의 삭제해서 다시 시작하지 마세요.

클라우드 모드에서도 **추억 보관**으로 현재 공유 월드를 파일로 내보낼 수 있습니다. **추억 불러오기**는 로컬 모드에서만 가능합니다. 클라우드를 켜거나 끄더라도 기존 `pocket-friends-v1`과 IndexedDB 원본을 클라우드 값으로 덮어쓰지 않습니다.

## 5. 실제 연결 후 확인할 항목

이 항목은 프로젝트 설정 후 직접 확인해야 하며, 자동 테스트로 실제 외부 서비스까지 검증했다고 표시하지 않습니다.

1. PC에서 상점의 간식을 구매합니다. 모바일에서 수 초 안에 코인이 줄고 인벤토리에 간식이 생기는지 확인합니다.
2. 모바일에서 아이템을 사용하고 PC에서도 수량·상태가 반영되는지 확인합니다.
3. Realtime이 연결되지 않으면 5초마다 서버 상태를 확인합니다. **새로 동기화**로 직접 확인할 수도 있습니다.
4. 탐험 귀환과 시간에 따른 상태 변화는 접속 중 서버에 최대 30초 간격으로 요청해 정산합니다. 두 기기가 요청해도 보상은 한 번만 반영됩니다. 미접속 중에는 정산 요청이 없으므로 다음 접속 후 처리되며 중복 지급하지 않습니다.
5. 사진을 바꾸고 다른 기기에서도 보이는지 확인합니다. 이 모드에서 사진은 Supabase에 저장되며 인증된 기기들과 공유됩니다.
6. 네트워크를 끊고 구매를 시도합니다. 실패 안내가 보이고 로컬 코인이 임의 변경되지 않아야 합니다. 연결 복구 후 **같은 작업 다시 시도**를 눌러 한 번만 처리되는지 확인합니다.
7. **로그아웃** 후 비밀번호 화면으로 돌아가는지 확인합니다. 서버 멤버십도 지우므로 이전 토큰으로 데이터에 접근할 수 없습니다.
8. 새 시크릿 창에서 비밀번호 없이 게임 화면이 나타나지 않는지 확인합니다.

입장 권한은 7일 뒤 만료됩니다. 브라우저를 닫아도 Supabase 세션을 유지하지만 만료되면 다시 비밀번호를 입력합니다. 다른 기기에서의 로그아웃은 해당 기기 권한에만 적용됩니다. 모든 기기를 차단하려면 Supabase SQL Editor에서 `delete from public.game_members;`를 실행하세요. **이 작업은 모든 기기의 재입장을 요구하지만 게임 월드 데이터는 삭제하지 않습니다.** 비밀번호를 바꾸지 않으면 기존 비밀번호를 아는 사용자는 다시 입장할 수 있습니다.

## 6. 서버 처리 구조와 데이터 보존

- Edge Function은 매 요청에서 `auth.getUser()`로 기기 JWT를 검증하고, 만료되지 않은 `game_members` 권한을 확인합니다. Anonymous Auth 세션만 있어서는 데이터를 읽지 못합니다.
- RLS는 멤버에게만 공유 월드를 읽게 하고, 클라이언트의 직접 쓰기와 게임 RPC 호출은 금지합니다. 서비스 역할 키는 Edge Function에서만 사용합니다.
- 최초 가져오기만은 소유자가 선택한 로컬 백업을 신뢰합니다. 형식과 범위는 검사하지만, 기존 로컬 게임에는 서버 서명이 없으므로 과거 코인·보상의 진위를 소급 증명할 수 없습니다. 이 예외는 빈 월드에서 한 번만 허용하며 이후에는 명령만 받습니다.
- 브라우저는 `buy`, `use`, `expedition`, `attendance`, `pet` 같은 **명령**을 보내며 새 잔액·경험치·확률 결과를 보내지 않습니다. 기존의 게임 규칙을 서버에서 실행합니다. B단계 이전이므로 기존 무료 먹이와 즉시 씻기 규칙도 아직 유지합니다.
- 서버 기준 시간으로 쿨타임과 탐험을 처리하며 탐험 결과의 난수는 서버의 암호학적 난수 생성기로 만듭니다. 특별 교감의 2초도 서버가 측정합니다.
- 데이터베이스 행 잠금 + revision 비교 + 명령 UUID 영수증을 한 트랜잭션에서 처리합니다. 충돌 시 최신 월드에서 다시 계산합니다. 이미 완료된 UUID는 재평가 전에 영수증을 확인합니다.
- 전송 결과가 불명확한 명령은 같은 탭의 sessionStorage에 보관하며, 재시도할 때 같은 UUID를 사용합니다. 오프라인 보상을 임의로 쌓아서 합산하지 않습니다. 명확히 거부된 명령은 큐에서 제거하지만 통신 오류는 재시도 대상으로 남깁니다.
- 이동·표정·자동 말풍선은 기기에서 렌더링합니다. 매 프레임 좌표를 전송하지 않으며 드래그를 놓을 때의 최종 위치만 명령으로 보냅니다. 기기별 자율 이동 좌표가 순간적으로 같을 필요는 없습니다.
- 클라우드 모드의 브라우저 애니메이션은 포만감·친밀도·경험치·보상을 직접 변경하지 않습니다. 친구끼리 대화하는 모습은 유지하지만 서버 보상으로 별도 인정하지 않습니다.
- 전체 월드는 JSON 스냅샷으로 보관합니다. 현재는 기존 4명용 스키마이며 향후 단계에서 8명·목욕·가구·햄스터 필드를 추가해야 합니다. 아직 없는 콘텐츠의 동기화가 완료됐다는 뜻은 아닙니다.
- `game_operations`는 중복 방지 기록이므로 임의 삭제하지 않습니다. 이 버전에는 자동 정리 작업을 넣지 않았습니다. 장기간 운영할 때 데이터베이스 사용량과 기록 보관 정책을 별도로 검토해야 합니다.

## 7. 개발자가 검증한 항목과 남은 작업

실행 결과는 PR 설명과 작업 완료 보고를 기준으로 확인하세요. 다음 검사는 외부 비밀번호나 서비스 키 없이 수행할 수 있습니다.

```bash
npm ci
npm test
npm run build
npm run test:e2e
npm run test:cloud
```

- 단위/SQL 테스트는 실제 PostgreSQL 엔진을 사용하는 PGlite에서 마이그레이션 SQL, RLS 권한, 트랜잭션·동시 요청·중복 영수증·입장 제한·세션 해제를 검사합니다. Supabase Auth 토큰 확인은 테스트 대역을 사용합니다.
- 클라우드 브라우저 테스트는 실제 서버 핸들러와 로컬 테스트 저장소를 연결해 로그인·이전·두 기기·사진 보존·재시도·교감/드래그를 검사합니다. Supabase Auth와 네트워크는 테스트 대역이며 실제 Realtime 구독은 별도 검증이 필요합니다.
- CI는 Deno로 Edge Function을 타입 검사합니다. 서버용 npm 의존성은 `supabase/functions/deno.lock`으로 고정합니다. Deno가 프런트엔드의 불필요한 개발 의존성을 가져오지 않도록 `DENO_NO_PACKAGE_JSON=1`을 사용합니다.
- 실제 Supabase 프로젝트 배포, 실제 JWT/Realtime 연결, 운영 사이트에서 PC·모바일 연결, 실제 iOS Safari는 사용자 설정 후 확인이 필요합니다.
- 음식 구매 의무화, 30분 목욕, 수면, 개명, 새 확률표, 가구, 감기, 새 캐릭터, 햄스터는 다음 B~D단계입니다.

### 이 브랜치에서 실행한 결과

- `npm run test:cloud`: PC·모바일 클라우드 UI 검사 12개 통과(테스트 백엔드 사용).
- 기본 로컬 모드와 클라우드 활성화 모드의 `npm run build` 통과.
- Deno 서버 타입 검사 및 고정 의존성 검사 통과.
