# Supabase Egress 최적화 결과 및 운영 확인

2026-11-11, 기준 main `a867db9`, 작업 브랜치 `codex/egress-optimization`.

**코드/로컬 검증과 운영 반영은 별개다. 이 문서 작성 시점에 운영 배포 성공·Supabase 실사용 절감률은 아직 확인되지 않았다.** Git transport는 되지만 이 실행 환경의 GitHub API와 운영 HTTP 접근이 403으로 차단된다. 자동 PR 경로에 push하고, 기존 보호 정책의 PR 리뷰/병합과 release-approval을 거쳐야 한다. 완료하지 않은 단계를 성공으로 보고하지 않는다.

## ① 원인과 실제 수정

| 기존 경로 | 문제 | 수정 |
|---|---|---|
| `src/cloud/client.ts` watch/read | 5초마다 전체 월드 조회, 30초마다 별도 refresh, 같은 시점의 요청 중첩 | 변경 확인 요청에 knownRevision 전송. 읽기 요청 합치기, 진행 중 명령 응답 재사용. 활동 명령도 시간을 정산하므로 그 직후 중복 heartbeat 생략 |
| 같은 파일 postgres_changes 구독 | 월드 UPDATE 때 개인 사진을 포함한 전체 JSON이 각 접속 기기로 전달되고 다시 status 요청 | 새 클라이언트에서는 이 구독을 만들지 않음. 활성 화면에서 약 5초마다 작은 revision 확인으로 다른 기기 변경 감지. 동기화를 중단하는 방식은 아님 |
| `src/cloud/server.ts` status | 바뀌지 않아도 load 전체 데이터 반환 | 인증/회원 확인 후 id/revision/updated_at만 조회. 같은 revision이면 약 70~100바이트의 unchanged 응답 |
| 같은 파일 command 응답 | 행동마다 전체 월드 반환 | 클라이언트가 알고 있는 revision을 기준으로 변경분만 반환. 작은 하위 객체는 묶어 더 짧게 전송 |
| 같은 파일 명령 전후 load | 동일 월드를 DB에서 다시 읽음 | 최대 3개 revision/60초의 isolate-local 캐시, 매번 DB revision 확인. CAS commit 직후 metadata가 정확히 expected+1일 때만 서버가 계산한 결과 재사용. 충돌·다른 기기 변경이면 재조회 |
| `supabase/functions/treasure/index.ts` load | 사용하지 않는 원본 log 등을 select *로 읽음 | 검증에 사용하는 명시적 필드만 선택. checkpoint/hash/seed/규칙/보상 결과는 보존 |
| 화면 숨김/오프라인/실패 | 숨겨진 화면도 주기 요청, 실패 시 반복 가능 | 숨김/오프라인 주기 요청 중단, 복귀/online에 즉시 확인. 실패 간격 증가, 5회 실패 후 자동 확인 정지; 사용자의 재시도·복귀·재연결로 다시 확인 |

5초는 변경 확인 목표 주기이며 네트워크 응답 시간/진행 중 명령에 따라 반영이 늦어질 수 있다. 내부 스케줄러는 1초마다 조건만 검사하고, 네트워크 요청은 5초 이상 간격으로 제한한다. 30초 상태 정산이 조회 중복 억제에 밀리지 않도록 별도 우선순위로 처리한다.

누적 sequential scan 횟수 자체를 Egress 바이트로 환산하지 않았다. 기존 world 조회는 이미 기본키 `id=home` 조건을 사용하며, 한 행 테이블의 scan 통계만으로 새 인덱스가 필요하다고 판단하지 않았다.

### 인증·권한

`admin.auth.getUser(token)`과 `game_members.expires_at` 확인은 **요청마다 그대로 실행**한다. 임의 JWT 디코딩으로 대체하거나 회원 권한을 만료까지 캐시하지 않는다. getSession은 기존 SDK 로컬 세션 재사용이며 SDK의 토큰 갱신을 유지한다. auth/user와 회원 조회 감소는 브라우저의 불필요한 요청 감소에 따른 결과다. RLS/SQL/서버 권한/비밀번호를 변경하지 않았다.

### 사천성·캐릭터·보상

사천성은 한 쌍마다 서버가 순서·연결 가능 여부·서버 시각을 확인한다. 묶음 처리로 경쟁 기록이나 탐험 제한시간을 바꾸지 않았다. 이번 사천성 개선은 전체 월드 반복 응답/Realtime 중복 전송 제거다. 따라서 사천성 자체 명령 수가 줄었다고 보고하지 않는다.

이동 애니메이션은 기존처럼 로컬에서 실행한다. 수동 드래그, hold-start, pet-special의 서버 측 시간 측정과 코인/보상 검증은 보존한다. 자연 상태 변화는 기존 서버 경과시간 정산을 유지하고 UI만으로 보상을 지급하지 않는다.

## ② 변경 전후 측정

원본: [EGRESS_MEASUREMENTS.json](EGRESS_MEASUREMENTS.json).
재현: `node --experimental-transform-types scripts/measure-egress.mts` (Node 24, 기준 git commit 필요).

실제 이전 main 핸들러를 git에서 읽어 새 핸들러와 동일한 오프라인 시나리오로 호출했다. 개인 사진을 포함하는 **53,800바이트 합성 월드**, 두 기기, 이상적인 5초 확인 스케줄을 사용했다. 사천성은 경쟁 한 판 32쌍 완료 및 다른 기기의 4회 조회다. 캐시 유지(warm)와 **매 요청 새 isolate(cold)**를 모두 측정했다. 숫자는 실제 JSON Response의 UTF-8 길이이며 운영 사용자 데이터는 사용하지 않았다.

| 시나리오 | 이전 요청 수 → 이후 | 이전 Edge 응답 바이트 | 이후 warm / cold | 응답 절감 warm / cold |
|---|---:|---:|---:|---:|
| 10분 대기, 두 기기 | 282 → 242 | 15,560,733 | 176,188 / 2,300,754 | 98.87% / 85.21% |
| 10분 돌보기 혼합, 두 기기 | 342 → 242 | 19,536,329 | 516,835 / 4,782,185 | 97.35% / 75.52% |
| 사천성 경쟁 한 판 | 39 → 39 | 2,171,955 | 382,824 / 382,819 | 82.37% / 82.37% |

요청 수 감소: 대기 14.18%, 돌보기 29.24%, 사천성 0%. 같은 수의 서버 명령을 유지해도 전체 데이터 대신 변경분을 보내 전송량이 줄어든다.

DB 월드 조회 응답도 계측했다: 대기 17,759,212 → warm 72,559 / cold 3,379,857바이트, 돌보기 25,231,960 → 75,273 / 8,114,299바이트, 사천성 4,006,546 → 58,539 / 2,169,973바이트. 내부 경로의 이 값을 Edge 바이트와 단순 합산해 Supabase 청구 Egress라고 부르지 않는다.

**한계:** HTTP/TLS 헤더, 압축, auth/member/RPC 응답 본문, 기존 Realtime 전송은 위 바이트 표에서 제외했다. Realtime 제거 효과를 임의의 숫자로 더하지 않았다. 브라우저에서는 실제 새 클라이언트를 별도 검증했지만, 표의 요청 수는 이상적인 스케줄 실험이며 실제 모바일/운영 로그 횟수와 동일하다고 주장하지 않는다. 사진 유무·월드 크기·기기 수·동시 플레이·isolate 재사용에 따라 결과가 달라진다. 70~90% 목표의 **전체 프로젝트 실사용 달성은 운영 계측 전 미확인**이다.

### 월간 예상치 — 가정한 시나리오만

두 기기가 매일 1시간, 30일 동안 동일 패턴을 사용한다고 가정하면 Edge 응답 본문은:

- 대기: 이전 약 2.801GB → 약 **0.032~0.414GB/월**.
- 돌보기 혼합: 이전 약 3.517GB → 약 **0.093~0.861GB/월**.

이는 위 본문 측정의 단순 외삽이며 총 Supabase 청구 Egress가 아니다. 사용 시간/기기 수/플레이 횟수가 두 배면 대략 그만큼 증가한다. 사용자 제공 4.76GB는 누적 기간이 명확하지 않아 월간 기준으로 환산하지 않았다. 이미 사용한 4.76GB가 이번 수정으로 되돌아오지는 않으며, 제공 수치 기준 남은 여유는 약 0.24GB다.

[PR 목록](https://github.com/kwonyoung1/pocket-friends/pulls) · [변경 비교](https://github.com/kwonyoung1/pocket-friends/compare/main...codex/egress-optimization) · [배포 실행](https://github.com/kwonyoung1/pocket-friends/actions/workflows/deploy.yml).

새 서버는 opt-in(`sync: delta-v1`) 요청에만 변경분을 보내고, 구 클라이언트에는 기존 전체 응답을 보낸다. 새 클라이언트도 구 서버의 전체 응답을 처리한다. 서버 선배포 뒤 웹 배포 순서를 지킨다. 오래 열린 브라우저는 새로고침해 새 코드를 받아야 전체 최적화가 적용된다.

서버 검증 실패 시 기존 workflow가 새 웹 배포를 차단한다. 실제 장애가 발생했다면 승인된 기존 artifact 웹 롤백을 사용하고 호환성을 확인한다. 이번 작업에서 DB/데이터 롤백이나 운영 장애 훈련을 실행하지 않았다.

## ⑤ 운영 확인과 무료 플랜 관리

1. 배포 Summary에서 game/treasure SHA health와 최종 웹 SHA/모바일 boot를 확인한다. 녹색 build만으로 배포 완료라 하지 않는다.
2. [게임](https://kwonyoung1.github.io/pocket-friends/)의 새 버전에서 로그인/동기화를 확인한다. 자동 live smoke는 운영 데이터에 쓰기 요청/보상 지급을 하지 않는다.
3. [Supabase Dashboard](https://supabase.com/dashboard/projects)에서 기존 조직/프로젝트의 Usage를 열어 배포 시점 사용량과 다음 24시간·72시간의 증가량을 기록한다. 같은 동시 기기/접속 시간/플레이 횟수로 일평균 증가량을 비교하고 `일평균 × 30`을 월간 예상치로 계산한다. 서로 다른 누적 기간의 API count를 Egress로 환산하지 않는다.
4. photo 및 권한 데이터는 비공개 동기화 상태이므로 공개 CDN 캐싱으로 전환하지 않았다. Cached Egress가 0이어도 이번 프로토콜 최적화 실패를 뜻하지 않는다.
5. 무료 장기 운영은 이용량에 달려 있어 보장할 수 없다. 이번 기간의 잔여 한도는 적으므로 운영 Usage를 확인하고, 증가 시 먼저 최신 클라이언트 보급/열린 구버전 탭/예상 밖 접속 기기/사진 크기/실패 반복을 조사한다. 기능 삭제나 무조건 동기화 중단으로 해결하지 않는다.
6. 24/72시간 지표 확인 후 필요하면 사진 별도 저장/배포, 작은 revision 알림용 서버 broadcast를 별도 설계한다. 저장 구조·트리거·스키마 변경이 필요한 추가 작업은 먼저 계획과 승인을 받는다.

## 최종 실행 기록

검증 완료 시 아래에 실제 테스트 결과와 원격 PR/배포 상태를 기록한다. 운영 배포/API가 막혔다면 미완료 상태를 그대로 유지한다.


- 전체 단위 테스트: **43파일 548개 통과** (`npm test`).
- 기존 자동화 테스트: **16개 통과** (`npm run test:automation`).
- TypeScript/Vite build 및 번들 검증 통과. 기존 큰 청크 경고는 남아 있다.
- 모바일 클라우드 29개 시나리오를 실행했다. 첫 실행의 상태 갱신/사천성 대기열/매치3 타이밍 실패를 조사·수정했으며, 해당 3개 재검증과 최종 관련 검증을 통과했다. 전체를 반복 실행한 것으로 보고하지 않는다.
- 최종 집중 실행: 사진/두 기기/오프라인/매치3 stage·challenge **4개 통과**. 이후 자연 회복/배경 refresh·사천성 대기열/두 기기 및 네 크기(360×800, 375×812, 390×844, 412×915) **3개 통과**.
- 최종 transport 테스트는 소수점·배열·속성 삭제·사진 보존·stale revision·prototype 경로 차단을 확인한다. 캐시 없는 상황과 다른 기기 CAS 충돌도 검증했다.
- 로컬에 Deno 실행 도구가 없어 실제 Edge Function Deno check/배포는 기존 CI에서 확인해야 한다. 기존 전체 browser/cloud 필수 검사도 CI에 그대로 남겨 두었다.
- 운영 공개 `version.json` 요청은 이 환경의 CONNECT proxy에서 HTTP 403. 이를 운영 사이트 장애로 단정하지 않는다. 운영 DB/API로 사용자 데이터를 조회·수정하지 않았다.
